# godot-kimodo

[English](README.md) | 日本語

文章からキャラクターアニメーションを生成する、Godot エディター用のアドオンです。

テキストからモーションを生成するモデル [kimodo.cpp](https://github.com/localai-org/kimodo.cpp) を、Godot から使えるようにします。
生成対象の骨格は、22 関節の SMPL-X、30 関節の SOMA、Unitree の 34 関節ロボット G1 の 3 つです。
アドオンは選択したモデルを実行し、その結果をシーン内の `Skeleton3D` にリターゲットして、通常の Godot の `Animation` として渡します。

保存されるのは素の `Animation` リソースです。
このアドオンにも、kimodo.cpp にも、生成に使った 15 GiB のモデルファイルにも依存しません。
エクスポートしたゲームには何も持ち込まれません。

Kimodo が出力するのは、XYZW 順の親ローカル四元数と、メートル単位のルート移動です。
フレームレートは 30 fps です。
いずれも Godot の流儀と一致するため、作業の中心は形式の変換ではなくリターゲットになります。

## 動作条件

条件を決めているのはアドオンではなくモデルです。

| | 必要なもの | 理由 |
|---|---|---|
| ディスク | **15.2 GiB** | モーション GGUF が 1.05 GiB、テキストバンドルが 14.14 GiB、あわせて 36 ファイル。3 つのモデルはサイズが 1% 以内の差しかなく、テキストバンドルは共通です |
| VRAM | 実用上 **2 GB**、下限は 1002 MiB | `token_embedding.weight` は 128,256 x 4096 の BF16 テンソル 1 つで 1,050,673,152 バイトあります。テンソルは複数のバッファに分割できないため、どの設定でもこれを下回れません |
| Vulkan | **1.2** | ggml-vulkan がこれ未満では初期化しません |
| プラットフォーム | x86_64 の Linux または Windows | kimodo.cpp が C++23 コンパイラーと GGML の Vulkan バックエンドを必要とするため、モバイルと Web は対象外です |
| Python | **3.9** 以降、または `uv` | SMPL-X の変換にだけ、それも一度だけ必要です。コンバーターは標準ライブラリー以外を import しないため、uv は依存解決ではなく Python のない環境への手段です |
| Godot | **4.4** 以降 | 拡張が `compatibility_minimum` として宣言している値であり、ビルドに使う godot-cpp のブランチでもあります。開発は 4.7 で行っています |

上の数値はいずれもピーク値であり、足し合わせた値ではありません。
テキストエンコーダーは、レイヤーのループに入る前にトークン埋め込みを解放します。
レイヤーもチャンクごとに解放してから次へ進みます。
モーションモデルの重みを読み込むのは、プロンプトのエンコードが終わったあとです。

Vulkan デバイスがない場合は CPU にフォールバックし、同じ数値が VRAM から RAM に移ります。
フォールバックは何も表示せずに起こります。
GPU を必須にする設定はありません。

## 導入

1. [リリース](https://github.com/shiena/godot-kimodo/releases)から `godot-kimodo-vX.Y.Z.zip` をダウンロードします。
   1 つのアーカイブで両方のプラットフォームに対応します。
2. アーカイブ内の `addons/kimodo` フォルダーを、プロジェクトの `addons/` にコピーします。
3. **Project Settings > Plugins** で **Kimodo** をオンにします。
   エディターの右側にドックが表示されます。

モデルファイルはアーカイブに含まれません。
初回の使用時にアドオンが一度だけダウンロードします。
例外は SMPL-X で、これだけは自分で変換する必要があります。
[モーションモデル](#モーションモデル)を参照してください。

自分でビルドする場合は[ソースからのビルド](#ソースからのビルド)を参照してください。

## モーションモデル

モーションを生成するモデルは 3 つあり、Setup ペインの **Model** で選択します。
違いは予測する骨格で、これが humanoid リグをどこまで動かせるかを決めます。

| モデル | 関節数 | 対応するボーン | モデルファイル |
|---|---|---|---|
| **SMPL-X** | 22 | 22 すべて | 自分で変換 |
| **SOMA** | 30 | 25。顎、目、指先が加わります | 公開済み |
| **Unitree G1** | 34 | 16。頭がなく、リグの 1 ボーンに単軸関節が 3 つ対応します | 公開済み |

テキストエンコーダーは 3 つで共通です。
そのためモデルを切り替えても、再ダウンロードは約 1 GiB だけです。

SOMA と G1 は **Download** でそのまま取得できます。
[NVIDIA Open Model License](https://www.nvidia.com/en-us/agreements/enterprise-software/nvidia-open-model-license/)のもとにあり、変換結果の再配布が認められているためです。

取得できないのは SMPL-X だけです。
`LocalAI-io/Kimodo-SMPLX-RP-v1-GGML` は変換済みの GGUF を配布していましたが、上流のライセンスが派生モデルの配布を禁じていたため、公開を取り下げました。
現在このリポジトリにはモデルカードしかありません。
そのため **Download** を何度クリックしても、この GGUF は不足したままです。

SMPL-X のチェックポイントを自分で変換することは認められています。
変換結果を再配布することは認められていません。
そのため Setup ペインの **Convert SMPL-X...** が、この作業を手元で実行します。

1. SMPL-X を選んだ状態で **Model page** をクリックします。
   ゲートのかかった [nvidia/Kimodo-SMPLX-RP-v1](https://huggingface.co/nvidia/Kimodo-SMPLX-RP-v1) が開きます。
   ここでライセンスに同意し、[Settings > Access Tokens](https://huggingface.co/settings/tokens) でトークンを発行します。
   この手順だけはアドオンが代わりに行えません。
2. 発行したトークンをトークン欄に貼り付けます。
3. **Convert SMPL-X...** をクリックします。
   1.05 GiB のチェックポイントを取得し、固定したリビジョンを記録し、コンバーターを実行します。
   作業中はディスクを 2.1 GiB ほど使います。
   このうち半分はチェックポイントで、変換後は削除できます。

コンバーターは kimodo.cpp 自身の `convert_motion_to_gguf.py` です。
GDScript で書き直すのではなく、ビルド時に `addons/kimodo/scripts/` へコピーしています。
上流がレビューしているパーサーであり、標準ライブラリー以外を import せず、バイナリー形式の読み取りを二重に持てば間違える箇所も二重になるためです。
アドオンは `PATH` 上の Python で実行し、Python のない環境では `uv run --no-project --python 3.12` にフォールバックします。

完了すると presence 行が更新され、36 ファイル揃った表示になります。

生成したクリップは骨格の名前を持ちません。
ヘッダーのない float の配列が 2 つあるだけです。
アドオンは配列の幅から、どのモデルが生成したものかを判別します。
22、30、34 はいずれも異なる幅だからです。
そのため以前のクリップはそのまま読めますし、選択中のモデルと違うモデルで生成したクリップも、実際の中身どおりに読み込まれます。

## 最初のクリップの生成

1. **Setup** ペインを開き、**Model** を選び、**Model directory** を確認します。
   ここがモデルファイルの保存先です。
2. **Download** をクリックし、完了まで待ちます。
   ダウンロードは 15.2 GiB あります。
   進捗はペインに 1 ファイルずつ表示されます。
   SMPL-X の場合、完了時にモーション GGUF が不足していると表示されますが、これは想定どおりです。
   [モーションモデル](#モーションモデル)の手順で変換します。
3. **Generate** でフレーム数を指定し、プロンプトを入力します。
4. **Generate** をクリックします。
   生成が終わるとクリップが **Motion** に表示され、**Preview** が同梱のマネキンで再生します。
5. 動かしたいリグを含むシーンを開きます。
   **Target** がそのシーンの `Skeleton3D` を検出し、関節のうち何個を対応付けられたかを表示します。
6. **Save** でクリップに名前を付け、**Bake** をクリックします。
   そのシーンの `AnimationPlayer` にアニメーションが追加されます。
   ファイルとして書き出す場合は **Save clip** をクリックします。

## ドック

ドックは 1 列です。
上から **Setup**、**Generate**、**Motion**、**Target**、**Save**、**Preview** の順に並びます。
各セクションは自分の行に結果を表示するため、応答はクリックしたボタンのすぐ近くに現れます。

### Setup

一度決めたら変更しない項目をまとめたペインです。
ファイルの保存先、取得するモデルファイル、生成器のマシンの使い方の 3 つを扱います。
通常は折り畳まれていますが、設定対象のファイルが不足していると自動的に開きます。

ここでの「不足」とは、テキストエンコーダーが読み込む 36 ファイルのいずれかがない状態を指します。
途中で止まったダウンロードは完了として扱わず、ペインが開きます。
状態はペイン内の presence 行とペインのツールチップの両方に表示されるため、折り畳んでも確認できます。

**Folders** には、容量を消費する 2 つのディレクトリを指定します。
モデルファイルの保存先と、生成したクリップの書き出し先です。
どちらもプロジェクトではなくマシンに属する設定です。

**Model** では、3 つの骨格のどれで生成するかを選びます。
ペインの他の項目はこの選択に従います。
ディスク上に必要な GGUF、その取得元リポジトリ、**Preview** でリグの代わりに立つマネキンの 3 つです。

**Convert SMPL-X...** は、誰も公開できないモデルのときだけ有効になります。
他の 2 つでは無効になり、その理由をツールチップに表示します。
**Model page** は選択中のモデルの Hugging Face ページを開きます。
SMPL-X の場合、ここがライセンスに同意する場所です。

**Weights** は、設定したリポジトリからモデルファイルを取得します。
取得したファイルはすべてマニフェストと照合します。
マニフェストを返さないリポジトリがあっても、失われるのはそのリポジトリのファイルだけです。
SMPL-X の GGUF を取得できない状態でもテキストバンドルをダウンロードできるのは、このためです。
公開されているリポジトリはいずれもアクセストークンを必要としません。
トークンの入力欄は、自分で用意した認証付きミラーを使う場合と、誰にとってもゲートのかかった SMPL-X のチェックポイントのためにあります。
Editor Settings の **Motion repo** を設定すると、選択中のモデルの公開リポジトリを上書きできます。

チェックポイント側はハッシュを公開していません。
照合できるのは Hugging Face が報告するサイズと curl の転送そのものだけです。
実際に読み取った SHA-256 は変換時に GGUF へ記録されます。
これが正直な置き場所です。

ダウンロードは既存のファイルを残すため、中断した取得を再開し、破損したファイルを修復します。
36 ファイルが揃った状態でクリックすると、確認ダイアログが表示され、実行内容を提示します。
マニフェストとサイズを比較し、一致しないファイルだけを取り直します。
そのため通常はマニフェスト以外を転送しません。
**Re-hash existing** をオンにすると、15.2 GiB を読み直して内容も照合します。
このとき確認ダイアログの文面も変わります。

転送には **curl** を使います。
これがアドオンの唯一の外部依存です。
curl は Windows 10 以降、macOS、および事実上すべての Linux ディストリビューションに同梱されています。
`HTTPRequest` ではなく curl を使う理由は、中断したファイルを途中から再開できるためです。
15 GiB を超える転送では、接続の切断は起こるかどうかではなく、いつ起こるかの問題になります。

**Runtime** については[実行時の環境変数](#実行時の環境変数)で説明します。

### Generate

フレーム数、デノイズのステップ数、シードを指定します。
続いてプロンプトを入力し、ボタンをクリックします。

**+ Add prompt** をクリックすると、クリップを次のプロンプトへ引き継げます。
プロンプトは最大 16 個まで指定できます。
「前へ歩く」、次に「座る」、次に「手を振る」という流れを、途切れのない 1 本のクリップとして生成します。

繋ぎ目は、別々のクリップをクロスフェードしたものではありません。
直前の区間の末尾が、ルート、全関節の位置、足首と手首の向きに対する拘束としてモデルに渡されます。
モデルはその拘束のもとで次の区間を生成するため、姿勢が引き継がれ、キャラクターは移動した距離を保ちます。

**Transition** では、この重なりのフレーム数を指定します。
重なりのフレームは加算されずに吸収されるため、クリップの長さは常に各プロンプトの合計になります。
Transition には、2 つ目以降のどのプロンプトよりも短い値を指定してください。
シーケンス内の 1 プロンプトは 300 フレームまでです。
単独のプロンプトであれば 10,000 フレームまで指定できます。

シーケンスの所要時間は、含まれるプロンプトの数に比例します。
8B のテキストエンコーダーがプロンプトごとに 1 回、デノイザーが区間ごとに 1 回動作します。

生成は別プロセスで実行します。
テキストエンコーダーは 8B の LLM2Vec です。
エディターと Vulkan デバイスを共有すると VRAM を奪い合い、生成に失敗したときにエディターも巻き込まれます。

classifier-free guidance の重みは、生成器のビルド時に決まる値です。
現在はどちらも 2.0 で、コマンドラインからは変更できません。

### Motion

出力ディレクトリ配下の全クリップを、新しい順に一覧表示します。
ここで選択したクリップが Target と Save の対象になるため、フォルダーを探さずに以前のテイクへ戻れます。
**Open folder** をクリックすると、そのフォルダーをファイルマネージャーで開きます。

クリップは、リネームするまで生成に使ったプロンプトで表示されます。
**Rename** はフォルダー自体に名前を付け、一覧にはその名前が表示されます。
同じプロンプトから作った 2 本のクリップを見分ける手段はこれだけです。
**Delete** はフォルダーをシステムのゴミ箱へ移動します。
1 本のクリップは GPU 時間にして数分ぶんであり、このボタンは読み込みボタンの隣にあるためです。

### Target

フィールドは 2 つあり、ベイクのたびに両方を使います。

**Skeleton** には、アニメーションを適用するリグを指定します。
値はボタンをクリックした時点で決まります。
選択中の `Skeleton3D`、選択がなければ開いているシーンで最初に見つかった `Skeleton3D` です。
下のレポートはエディターの選択に追従するため、そこに表示されているものがベイクの対象になります。

**Bone map** は、クリップを生成したモデルの関節名を、そのリグのボーン名に読み替える表です。
必要になるのは、リグのボーン名が `SkeletonProfileHumanoid` のものでない場合だけです。
このフィールドは `kimodo/paths/bone_map` 設定をそのセッションだけ上書きします。
空のあいだは、設定値をプレースホルダーとして表示します。

レポートには、モデル名、解決した関節の数、解決しなかった関節、レストポーズの高さの比が表示されます。

```
Skeleton3D  56 bones
SMPL-X: mapped 22/22, scale 0.999
every joint resolved
```

この数は関節数ではなく、humanoid プロファイルが受け取れる数に対する比です。
G1 はすべて解決した状態で `mapped 16/16` と表示されます。
残り 18 関節は、リグにボーンのない単軸だからです。

サンプルの表が `addons/kimodo/samples/smplx_bone_map.tres` にあり、設定の初期値もこのファイルです。
同じ場所に `soma_bone_map.tres` と `g1_bone_map.tres` もあります。
いずれも humanoid プロファイルと各モデルの関節名を対応付けているため、その名前をそのまま持つリグは有効なターゲットになります。
書式の記入例としても利用できます。
編集せずに、次のコマンドで作り直してください。

```sh
godot --headless --path project -s res://tools/make_bone_maps.gd
```

Mixamo や VRM をはじめとする他のリグでは、Godot 自身が表を作成できます。
`BoneMap` を作成し、プロファイルに `SkeletonProfileHumanoid` を設定してください。
インスペクターがスケルトンとの自動対応付けを提示します。

### Save

どちらのボタンも、Target が決定したスケルトンにリターゲットします。
違うのは結果の出力先だけです。
**Bake** は開いているシーンの `AnimationPlayer` に追加します。
**Save clip** は単体のリソースとして書き出し、そのあと FileSystem ドックで場所を表示します。

どちらのボタンも、開いているシーンに `Skeleton3D` が必要です。
アニメーションのトラックパスが、そのシーン内でのスケルトンのパスだからです。

**Clip name** で指定した名前は、アニメーション名とファイル名の候補の両方に使われます。
2 つの規則は内容が異なるため、両方に照らして検査します。
`AnimationLibrary` は `,` と `[` を拒否しますが、ファイル名はこれらを受け付けます。
反対に、ファイル名は `*`、`?`、`|` を拒否しますが、ライブラリーは受け付けます。

複数のクリップを `AnimationLibrary` にまとめる場合は、`AnimationPlayer` のアニメーションパネルを使ってください。

### Preview

Motion で読み込んだクリップを、ターゲットのリグではなく、アドオン同梱のマネキンで再生します。
ターゲットのリグは編集中のシーンに属しており、2 か所に同時に存在できないためです。

ビューポートをクリックすると操作対象になり、枠がエディターのアクセントカラーで表示されます。
この状態でドラッグすると視点が回転し、ホイールで拡大縮小します。
操作対象になる前のホイールは、背後のドックのスクロールに使われます。
Escape キーを押すか、ほかの場所をクリックすると解除されます。
スライダーはどちらの状態でも動作します。
ビューポート下のつまみをドラッグすると、縦幅が変わります。

カメラはルートに追従し、グリッドはワールドに固定されます。
移動量と接地は、いずれもグリッドを基準に読み取れます。

同梱のマネキンは、SMPL-X のモーションをデコードするレストポーズと同じ寸法で作成しています。
そのため 22 関節すべてが scale 1.0 で対応し、調整なしで床に立ちます。
左半身が暖色、右半身が寒色で、顔にマーカーがあります。
一様に灰色の人形では、左右が反転したクリップを判別できないためです。
このモデルを削除してもアドオンは動作し、プレビューは手続き的なカプセルで代替します。

## 設定

アドオンが保持する設定はすべてエディター設定で、Editor Settings の `kimodo/` 以下にあります。
`project.godot` には何も書き込みません。
アドオンはエディター内でのみ動作し、エクスポートには含まれないため、設定が実行中のゲームに届く必要がないからです。
また、モデルファイルや出力先を別のドライブに向けるのは個人の環境の問題です。
バージョン管理下のファイルの変更として現れるべきではありません。

20 項目すべてがプラグインの読み込み時に宣言されます。
そのため、ドックが値を書き込む前から、Editor Settings のダイアログが範囲やファイルフィルターや列挙付きで一覧表示します。

エディター設定は、プロジェクトではなくエディターに属します。
これが影響するのは、唯一の `res://` パスであるボーンマップです。
同じエディターで次に開いたプロジェクトにも、この値が引き継がれます。
保存されたパスが現在のプロジェクトに存在しない場合、アドオンは同梱のサンプルにフォールバックします。
開けないファイルをリターゲット処理に渡さないためです。

プロンプトとシードはどこにも保存しません。
これらは 1 回の実行にだけ属する値です。

### 実行時の環境変数

kimodo.cpp は設定を環境変数から読み込みます。
ここからプロセスに環境を直接渡す手段がないため、ドックはエディター側に環境変数を設定し、生成器に継承させます。

| 設定 | 変数 | 効果 |
|---|---|---|
| チャンクあたりのテキストレイヤー数 | `KIMODO_TEXT_LAYER_CHUNK` | 1〜32、デフォルトは 8。減らすと VRAM のピークが下がり、速度が落ちます |
| バックエンド | `KIMODO_BACKEND` | 効果があるのは `cpu` という文字列だけです。それ以外の値はすべて「Vulkan を試し、失敗したら CPU」を意味します |
| CPU スレッド数 | `KIMODO_THREADS` | CPU バックエンドでのみ有効です。0 を指定するとマシンに任せます |
| GPU 番号 | `GGML_VK_VISIBLE_DEVICES` | kimodo.cpp は常に Vulkan のデバイス 0 を開きます。GPU の選択は、どのデバイスを 0 にするかの並べ替えになります |
| システムメモリーへの退避 | `GGML_VK_ALLOW_SYSMEM_FALLBACK` | デバイスローカルの VRAM が不足したとき、バッファーをホストメモリーに配置します。以後アクセスのたびに PCIe を経由するため、速度ではなく完走を優先する設定です |

Windows では、kimodo.cpp の FP32 パリティガードがコンパイル対象から外れます。
このガードが Unix 向けに書かれているためです。
その結果 `GGML_VK_DISABLE_COOPMAT`、`GGML_VK_DISABLE_COOPMAT2`、`GGML_VK_DISABLE_F16` が設定されず、cooperative-matrix 経路が F32 の参照重みを FP16 に変換する場合があります。
出力を参照実装とビット単位で一致させる必要がある場合は、これらを手動で設定してください。

## 制限

**左右はモデルに対して未検証です。**
座標系、接地、正面軸については生成されたモーションで確認済みで、Kimodo は +Z 方向へ歩きます。
一方、関節が体のどちら側に属するかは、同じ方法では確認できていません。
自動テストは合成のフィクスチャーを使うため、こちらでも確認できません。
片方の手を名指しで挙げさせるプロンプトを与えれば判定できます。

**レストポーズは近似値です。**
レストポーズはモーション GGUF に含まれないため、アドオンは上流の参照実装から較正した表を保持しています。
この表はわずかに左右非対称で、膝が脚の自然な範囲より外へ張り出します。
リターゲットのスケールも、この表を基準に測定しています。
モデルファイルがレストポーズを直接提供するようになれば、この表は不要になります。

**SOMA と G1 の対応付けは未検証です。**
SMPL-X は生成したモーションで確認済みですが、他の 2 つは確認していません。
クリップを 1 本得るだけでもモデルファイルと GPU での実行、そして比較対象が必要になるためです。
各関節がどの humanoid ボーンを動かすかは、関節名とレストポーズのオフセットからの読み取りであり、読み取りは誤りうるものです。
特に G1 は、股関節の単軸 3 関節を 1 本の大腿ボーンに対応付けるとき、3 つのうち最後のものを採用しています。
これは名前が示すとおり pitch、roll、yaw の順に連なっている場合には正しい判断です。

**手首から先は動きません。**
SMPL-X は体の 22 関節で終わります。
SOMA がそれに加えるのは顎、両目、片手につき指先 1 つで、手と呼べるものではありません。
`SkeletonProfileHumanoid` は 56 ボーンあるため、どのモデルで生成したクリップでも、フルリグのキャラクターでは指がレストポーズのまま残ります。

## ソースからのビルド

ビルドには SCons、Python 3、C++17 のツールチェーンが必要です。
ツールチェーンは Windows では MSVC、Linux では GCC または Clang です。

```sh
git submodule update --init --recursive
scons
```

ビルドの出力先は `project/addons/kimodo/bin/<platform>/` で、`project/addons/kimodo/kimodo.gdextension` が参照する場所もここです。
すべてがアドオンのフォルダー内にあります。
そのため `addons/kimodo` が、リリースの内容のすべてであり、プロジェクトにコピーする対象のすべてでもあります。
ドックは GDScript のため、ドック自体のビルドは不要です。

同じ実行で、kimodo.cpp の `convert_motion_to_gguf.py` を `project/addons/kimodo/scripts/` にコピーします。
これも `bin/` もリポジトリには含めません。
配布されるコピーが、固定した submodule のリビジョンのものになり、二重管理が発生しないためです。

リリースするライブラリーは単精度のみです。
倍精度の Godot を使う場合は `scons precision=double` でビルドし、対応する行を `.gdextension` に追加してください。

### kmd-generate

同じ `scons` の実行が、kimodo.cpp から `kmd-generate` をビルドします。
`kmd-generate` が読み込む共有ライブラリーとともに、拡張と同じ場所に配置します。
ドックは最初にこの場所を参照するため、ビルドが成功していれば設定なしで生成できます。

SCons は自前でコンパイルせず、CMake を実行します。
そのビルドを再現するには、GGML と Vulkan シェーダーのコンパイルまで再現することになるためです。
SCons と C++ ツールチェーンのほかに、次のものが必要です。

- cmake 3.25 以降
- Vulkan SDK（GGML の Vulkan シェーダーをコンパイルする `glslc` のため）
- kimodo.cpp 内の `ggml` サブモジュール（`git submodule update --recursive` で取得されます）

いずれかが不足している場合は、失敗ではなく警告付きのスキップになります。
`kmd-generate` が以前に生成したモーションを読み込み、リターゲットし、保存する用途では、アドオンはそのまま動作するためです。
意図的にスキップする場合は `kimodo_native=no` を指定します。

Windows では、SCons が検出済みの MSVC 環境を CMake に渡すため、開発者コマンドプロンプトは不要です。
Visual Studio のコンポーネントとして入る cmake も検出するため、PATH に用意する必要もありません。
成果物はおよそ 55 MB で、その大半は `ggml-vulkan.dll` に埋め込まれた Vulkan シェーダーです。

ビルドツリーは `kimodo.cpp/build/` 配下にターゲットごとに作られます。
そのため、1 つのチェックアウトから複数のプラットフォームをビルドしても CMake キャッシュは競合しません。

### kimodo.cpp へのパッチ

kimodo.cpp が文書化しているのは Linux でのビルドで、固定しているリビジョンは MSVC でコンパイルできません。
修正は `patches/` にあり、SCons が configure の前にサブモジュールの作業ツリーへ適用します。
ローカルの変更として埋もれず、パッチとして残す形にしています。
適用済みのパッチはスキップされます。

| パッチ | 修正内容 |
|---|---|
| `0001-narrow-path-for-gguf_init_from_file.patch` | Windows では `std::filesystem::path::value_type` が `wchar_t` のため、`path.c_str()` が `gguf_init_from_file` の受け取る狭い文字列になりません |
| `0002-include-stdexcept.patch` | `<stdexcept>` を include せずに `std::runtime_error` を使用しています。libstdc++ は推移的に取り込みますが、MSVC の STL は取り込みません |

どちらも本来は上流に取り込まれるべき修正です。
`.gitmodules` で kimodo.cpp に `ignore = dirty` を指定しているため、パッチを適用した作業ツリーが `git status` のたびに変更として表示されることはありません。
サブモジュールが指すのは固定リビジョンのままです。

### 継続的インテグレーション

各プラットフォームを、それぞれのランナーでネイティブのツールチェーンによりビルドします。
`ubuntu-24.04` では GCC、`windows-2022` では MSVC です。
MSVC を選ぶ理由は 3 つあります。

- kimodo.cpp の CMake 設定が MSVC 向けの分岐を持つこと
- `patches/` のパッチが MSVC を対象としていること
- ggml 自身の CI が Windows 向け Vulkan ビルドに MSVC を使っていること

残りはプラットフォームごとに `.github/actions/setup-build` が導入します。
`glslc` は両方のプラットフォームで必要なため、Vulkan SDK も導入対象です。

`ci.yml` は push のたびに両方のターゲットをビルドします。
`make_build.yml` はバージョン番号を指定して手動で実行します。
両方の target type をビルドし、4 つのライブラリーと SMPL-X のコンバーターを収めた `addons/kimodo` を組み立て、GitHub のリリースに zip として公開します。
コンバーターは Linux のリリースビルドから取ります。
どのプラットフォームでも同じファイルであり、scons を実行しないと存在しないためです。
コミットするのは `plugin.cfg` だけです。
ビルドしたライブラリーはリポジトリに入れず、リリースの成果物として配布するためです。

クロスコンパイルは可能ですが、検証していません。
`KIMODO_CMAKE_TOOLCHAIN` で CMake のツールチェーンを指定し、`KIMODO_CMAKE_ARGS` で configure の行に引数を追加すれば、ビルドの仕組みとしては足ります。
障害になるのは、Vulkan ローダーの mingw 用インポートライブラリーが存在しないことです。
ggml-vulkan はこれをリンク時に必要とします。

### テスト

```sh
godot --headless --path project --import
godot --headless --path project -s res://tools/verify_stage1.gd
godot --headless --path project -s res://tools/verify_stage2.gd
godot --headless --path project -s res://tools/verify_stage4.gd
```

stage 1 は、ファイルレイアウト、四元数の成分順、順運動学、そしてベイクした `Animation` がトラックの指すボーンを実際に動かすことを検証します。
stage 2 はリターゲットを検証します。
対象は 3 つです。
`BoneMap` 越しに接頭辞付きのボーン名を持つリグ、単位行列でないレストポーズの回転、対応済みの 2 ボーンに挟まれた未対応のツイストボーンです。
stage 4 は保存とライブラリー管理を検証します。

3 つとも合成のフィクスチャーを使うため、検証できるのは処理の接続だけです。
モデル自身の流儀については何も検証しません。

### プレビュー用シーン

`project/smplx_preview.tscn` はクリップを再生し、目で判断するしかない値を表示します。
表示するのは、ルート位置、両手、腰の正面ベクトル、そして最も低いボーンと地面との距離です。
T キーを押すとターゲットが切り替わります。
順序は、素の SMPL-X レストポーズ、リターゲット経路を通した humanoid 名のレストポーズ、読み込んだモデルです。

実際のモデルファイルがない場合は、まず合成のクリップを作成してください。
このクリップは +Z 方向へ歩きながら左腕を上げるため、左右の反転や 180 度の向きの誤りがあればすぐに判別できます。

```sh
python scripts/make_sample_motion.py project/motion_sample
```

作成後は `project/` を Godot で開いて実行するか、実際の出力を指定します。

```sh
godot --path project -- --motion=/path/to/kmd-generate/out
```

ドラッグで視点が回転し、ホイールで拡大縮小します。
Space キーで再生と一時停止を切り替え、左右の矢印キーで 1 フレームずつ進みます。

### マネキン

`addons/kimodo/samples/kimodo_mannequin.glb` は 40 KB、22 ボーン、300 三角形です。
リポジトリが保持しているのはモデルのソースではなく生成手順です。
編集せずに、次のコマンドで作り直してください。

```sh
blender --background --python scripts/make_mannequin.py
```

ボーンは SMPL-X のレストポーズから配置しており、`SkeletonProfileHumanoid` の名前を最初から持っています。
プレビューがボーンマップなしで、インポート時のレストポーズ補正もなしに使えるのはこのためです。

同梱しているのは SMPL-X の分だけです。
SOMA と G1 は、それぞれのレストポーズから生成したカプセルにフォールバックします。
見栄えは劣りますが、表示としては正しいものです。
モデルごとにマネキンの設定が `kimodo/paths` にあるため、自作の図形を指定できます。
条件は同梱のものと同じで、`SkeletonProfileHumanoid` のボーン名を持ち、レストポーズで床に立っていることです。
