# godot-kimodo

[English](README.md) | 日本語

文章からキャラクターアニメーションを生成する、Godot エディタ用のアドオンです。

テキストから SMPL-X のスケルタルアニメーションを作る [kimodo.cpp](https://github.com/localai-org/kimodo.cpp) を、Godot から使えるようにします。
モデルを実行し、結果をシーン内の `Skeleton3D` にリターゲットして、ふつうの Godot の `Animation` として渡します。

保存されるのは素の `Animation` リソースです。
このアドオンにも kimodo.cpp にも、生成に使った 15 GiB の重みにも依存しません。
したがって、エクスポートしたゲームには何も持ち込まれません。

Kimodo が出力するのは、XYZW 順の親ローカル四元数と、メートル単位のルート移動で、30 fps です。
3 つとも Godot の流儀と一致します。
作業の大半が変換ではなくリターゲットなのは、そのためです。

## 動作条件

条件を決めているのはアドオンではなくモデルです。

| | 必要なもの | 理由 |
|---|---|---|
| ディスク | **15.2 GiB** | モーション GGUF が 1.05 GiB、テキストバンドルが 14.14 GiB、あわせて 36 ファイル |
| VRAM | 実用上 **2 GB**、下限は 1002 MiB | `token_embedding.weight` は 128256 x 4096 の BF16 テンソル 1 つで 1,050,673,152 バイトあり、テンソルは複数のバッファに分割できません。どう設定してもこれを下回れません |
| Vulkan | **1.2** | ggml-vulkan がこれ未満では初期化を拒否します |
| プラットフォーム | x86_64 の Linux または Windows | kimodo.cpp が C++23 コンパイラと GGML の Vulkan バックエンドを要求するため、モバイルと Web は対象外です |
| Godot | **4.4** 以降 | 拡張が `compatibility_minimum` として宣言している値であり、ビルドに使う godot-cpp のブランチでもあります。開発は 4.7 で行っています |

これらはピーク値であって、足し合わせた値ではありません。
テキストエンコーダはレイヤーのループに入る前にトークン埋め込みを解放し、チャンクごとに解放してから次へ進みます。
モーションの重みが読み込まれるのは、プロンプトのエンコードが終わってからです。

Vulkan デバイスが無い場合は CPU にフォールバックし、同じ数値が VRAM から RAM に移ります。
このフォールバックは何も告げずに起こり、GPU を必須にする設定はありません。

## 導入

[リリース](https://github.com/shiena/godot-kimodo/releases)から `godot-kimodo-vX.Y.Z.zip` を取得し、中の `addons/kimodo` フォルダをプロジェクトの `addons/` にコピーします。
1 つのアーカイブで両プラットフォームを賄います。
プロジェクト設定のプラグインから **Kimodo** を有効にすると、右側にドックが現れます。

重みはアーカイブに含まれません。
初回の使用時に、アドオンが一度だけダウンロードします。

自分でビルドする場合は[ソースからのビルド](#ソースからのビルド)を参照してください。

## 最初の 1 本

1. **Setup** ペインを開き、重みの置き場所である **Model directory** を確認します。
   **Download** を押したら放置してください。
   15.2 GiB には時間がかかり、ペインが 1 ファイルずつ進捗を報告します。
2. **Generate** でフレーム数を決め、プロンプトを入力して **Generate** を押します。
   完了するとクリップが **Motion** に現れ、**Preview** が同梱のマネキンで再生します。
3. 動かしたいリグを含むシーンを開きます。
   **Target** がその `Skeleton3D` を見つけ、22 関節のうち何個を対応付けられたかを報告します。
4. **Save** でクリップに名前を付け、**Bake** でそのシーンの `AnimationPlayer` に載せるか、**Save clip** でリソースとして書き出します。

## ドック

1 列で、上から順に **Setup**、**Generate**、**Motion**、**Target**、**Save**、**Preview** と並びます。
各セクションが自分の行で応答を返すので、答えは押したボタンのすぐ横に出ます。

### Setup

一度決めたら触らない部分を持ちます。
ファイルの置き場所、どの重みを取ってくるか、生成器がマシンをどう使うかです。
折り畳まれたままですが、設定対象のファイルが欠けていると自分で開きます。

「欠けている」とは、テキストエンコーダが読む 36 ファイルのいずれかが無い状態を指します。
途中で止まったダウンロードは完了とは見なされず、ペインが開きます。
状態はペイン内の presence 行とペイン自身のツールチップの両方にあるので、折り畳んでも答えは残ります。

**Folders** は容量を食う 2 つのディレクトリを持ちます。
重みの置き場所と、生成したクリップの書き出し先です。
どちらもプロジェクトではなくマシンに属します。

**Weights** は公開されている 2 つのリポジトリを取得し、全ファイルをマニフェストと照合します。
どちらもアクセストークンを必要としません。
トークン欄はゲートのかかったミラー用です。

ダウンロードは既にあるファイルを残すので、中断した取得を再開し、壊れたファイルを修復します。
36 ファイルが揃った状態で押すと確認を出し、実際に何をするかを述べます。
マニフェストとサイズを比べ、食い違うものだけを取り直すので、通常はマニフェスト 2 つ以外は転送しません。
**Re-hash existing** を有効にすると 15.2 GiB を読み直して中身も照合し、確認の文面もそう変わります。

転送には **curl** を使います。
これがアドオンの唯一の外部依存です。
Windows 10 以降、macOS、そして事実上すべての Linux ディストリビューションに同梱されています。
`HTTPRequest` ではなく curl なのは、途中まで落ちたファイルを再開できるためです。
15 GiB を超える転送では、接続が切れるかどうかではなく、いつ切れるかが問題になります。

**Runtime** については[実行時の環境変数](#実行時の環境変数)で説明します。

### Generate

フレーム数、デノイズのステップ数、シードを決め、プロンプトを書いてボタンを押します。

**+ Add prompt** はクリップを次のプロンプトへ引き継ぎます。
最大 16 個まで並べられます。
「前へ歩く」、次に「座る」、次に「手を振る」を、途切れのない 1 本として作れます。

繋ぎ目は別々のクリップのクロスフェードではありません。
直前の区間の末尾が、ルート、全関節の位置、足首と手首の向きに対する拘束としてモデルに渡され、そこから次の区間が生成されます。
だから姿勢が引き継がれ、キャラクターは進んだ距離を保ちます。

**Transition** はその重なりを何フレーム与えるかです。
このフレームは加算されずに吸収されるので、クリップの長さは常にプロンプトの合計になります。
Transition は 2 つ目以降のどのプロンプトよりも短くなければなりません。
シーケンス内の 1 プロンプトは 300 フレームまでです。
単独のプロンプトなら 10000 フレームまで指定できます。

シーケンスの所要時間は、含まれるプロンプトの数に比例します。
8B のテキストエンコーダがプロンプトごとに 1 回、デノイザーが区間ごとに 1 回走ります。

生成は別プロセスで実行します。
テキストエンコーダは 8B の LLM2Vec で、エディタの Vulkan デバイスを共有すると VRAM を奪い合い、生成の失敗がエディタを道連れにします。

classifier-free guidance の重みは生成器のビルド時に決まった値で、現在はどちらも 2.0 です。
コマンドラインからは設定できません。

### Motion

出力ディレクトリ配下の全クリップを、新しい順に並べます。
ここで選んだものが Target と Save の対象になるので、フォルダを探し回らずに以前のテイクへ戻れます。
**Open folder** はそのフォルダをファイルマネージャで開きます。

クリップはリネームするまで、生成に使ったプロンプトで表示されます。
**Rename** はフォルダ自体に名前を付け、一覧はその名前を表示します。
同じプロンプトの 2 本を見分ける手段はこれだけです。
**Delete** はフォルダをシステムのゴミ箱へ移します。
1 本のクリップは GPU 時間にして数分ぶんであり、このボタンは読み込みボタンの隣にあるためです。

### Target

2 つのフィールドがあり、ベイクのたびに両方とも使われます。

**Skeleton** は動かす先のリグです。
ボタンを押した瞬間に解決されます。
選択中の `Skeleton3D`、無ければ開いているシーンで最初に見つかったものです。
下のレポートはエディタの選択に追従するので、そこに書かれているものがベイクの対象になります。

**Bone map** は SMPL-X の関節名を、そのリグのボーン名に読み替える表です。
必要になるのは、リグの名前が `SkeletonProfileHumanoid` のものでない場合だけです。
このフィールドは `kimodo/paths/bone_map` 設定をそのセッションだけ上書きするもので、空のあいだは設定値をプレースホルダとして表示します。

レポートは 22 関節のうち何個が解決したか、何が解決しなかったか、レストポーズの高さの比を示します。

```
Skeleton3D  56 bones
mapped 22/22, scale 0.999
every joint resolved
```

サンプルの表が `addons/kimodo/samples/smplx_bone_map.tres` にあり、設定の初期値もここを指しています。
humanoid プロファイルと SMPL-X の関節名を対応付けるので、その名前をそのまま持つリグは有効なターゲットになります。
形式の実例としても読めます。

Mixamo や VRM をはじめ他のリグについては、Godot 自身が表を作れます。
`BoneMap` を作成してプロファイルを `SkeletonProfileHumanoid` に設定すると、インスペクタがスケルトンとの自動対応付けを提示します。

### Save

どちらのボタンも Target が解決したスケルトンにリターゲットするもので、違うのは結果の行き先だけです。
**Bake** は開いているシーンの `AnimationPlayer` に載せます。
**Save clip** は単体のリソースとして書き出し、そのあと FileSystem ドックで所在を示します。

どちらも開いているシーンに `Skeleton3D` が必要です。
アニメーションのトラックパスが、そのシーン内でのスケルトンのパスだからです。

**Clip name** はアニメーションの名前になり、ファイル名の候補にもなります。
2 種類の規則の両方に照らして検査します。
`AnimationLibrary` は `,` と `[` を拒否しますが、ファイル名はこれらを受け付けます。
逆にファイル名は `*`、`?`、`|` を拒否しますが、ライブラリは受け付けます。

複数のクリップを `AnimationLibrary` にまとめるには、`AnimationPlayer` 自身のアニメーションパネルを使ってください。

### Preview

Motion が読み込んだクリップを、ターゲットのリグではなくアドオン同梱のマネキンで再生します。
リグは編集中のシーンに属していて、2 か所に同時に存在できないためです。

ビューポートをクリックすると操作権を取り、枠がエディタのアクセントカラーで光ります。
そのあいだドラッグで orbit、ホイールで zoom します。
取る前のホイールは、下にあるドックのスクロールに属します。
Escape で解放でき、他の場所をクリックしても同じです。
スライダーはどちらの状態でも動き、ビューポート下のつまみをドラッグすると縦幅が変わります。

カメラはルートに追従し、グリッドはワールドに固定されます。
移動量も接地も、これを基準に読み取れます。

マネキンはモーションのデコードに使うレストポーズと同じ寸法で作ってあるので、22 関節すべてが scale 1.0 で対応し、調整なしで床に立ちます。
左半身が暖色、右半身が寒色で、顔にマーカーがあります。
一様に灰色の人形では、左右が反転したクリップを見分けられないためです。
モデルを取り除いてもアドオンは動きます。
プレビューは手続き的なカプセルにフォールバックします。

## 設定

アドオンが記憶するものはすべてエディタ設定で、Editor Settings の `kimodo/` 以下にあります。
`project.godot` には何も書きません。
アドオンはエディタの中だけで動き、エクスポートには含まれないので、設定が実行中のゲームに届く必要がありません。
一方で、重みや出力先を別のドライブに向けるのは個人の答えであって、追跡対象ファイルの変更として現れるべきものではありません。

16 項目すべてがプラグインの読み込み時に宣言されるので、ドックが何も書く前から、Editor Settings のダイアログが範囲やファイルフィルタや列挙付きで一覧します。

エディタ設定はプロジェクトではなくエディタに属します。
これが効いてくるのが、唯一の `res://` パスであるボーンマップです。
同じエディタで次に開いたプロジェクトにも持ち越されます。
保存されたパスが現在のプロジェクトに無い場合、アドオンは開けないファイルをリターゲッタに渡す代わりに、同梱のサンプルにフォールバックします。

プロンプトとシードはどこにも保存しません。
これらは 1 回の実行に属します。

### 実行時の環境変数

kimodo.cpp は設定を環境変数から読みます。
ここからプロセスに環境を直接渡す手段が無いので、ドックはエディタ側に設定し、生成器に継承させます。

| 設定 | 変数 | 効果 |
|---|---|---|
| チャンクあたりのテキストレイヤー数 | `KIMODO_TEXT_LAYER_CHUNK` | 1 から 32、既定は 8。減らすと VRAM のピークが下がり、速度を失います |
| バックエンド | `KIMODO_BACKEND` | 効果があるのは `cpu` という文字列だけです。それ以外はすべて「Vulkan を試し、駄目なら CPU」を意味します |
| CPU スレッド数 | `KIMODO_THREADS` | CPU バックエンドでのみ効きます。0 はマシン任せです |
| GPU 番号 | `GGML_VK_VISIBLE_DEVICES` | kimodo.cpp は常に Vulkan のデバイス 0 を開くので、GPU を選ぶ操作は、どれをデバイス 0 にするかの並べ替えになります |
| システムメモリへの退避 | `GGML_VK_ALLOW_SYSMEM_FALLBACK` | デバイスローカルの VRAM が尽きたときバッファをホストメモリに置きます。以後アクセスのたびに PCIe を渡るので、速度ではなく完走を買う設定です |

Windows では kimodo.cpp 自身の FP32 パリティガードがコンパイルから外れます。
Unix 向けに書かれているためです。
そのため `GGML_VK_DISABLE_COOPMAT`、`GGML_VK_DISABLE_COOPMAT2`、`GGML_VK_DISABLE_F16` が設定されず、cooperative-matrix 経路が F32 の参照重みを FP16 に変換する可能性があります。
出力を参照実装とビット単位で一致させる必要があるなら、手で設定してください。

## 制限

**左右はモデルに対して未検証です。**
座標系、接地、正面軸は生成されたモーションで確認済みで、Kimodo は +Z 方向へ歩きます。
関節が体のどちら側に属するかは、同じようには確認できていません。
自動テストは合成のフィクスチャに対して走るので、こちらでも確認できません。
片方の手を名指しで挙げさせるプロンプトがあれば決着します。

**レストポーズは近似です。**
モーション GGUF に含まれていないので、アドオンは上流の参照実装から較正した表を持っています。
この表はわずかに左右非対称で、膝が脚の自然な範囲より外へ張り出します。
リターゲットのスケールもこの表を基準に測っています。
モデルファイルがレストポーズを直接提供するようになれば、この表は不要になります。

**使うのは体の 22 関節だけです。**
Kimodo は SMPL-X ですが、このアドオンが読むのは体のスケルトンだけで、手と顔は読みません。
`SkeletonProfileHumanoid` は 56 ボーンあるので、フルリグのキャラクターでは指がレストポーズのまま残ります。

## ソースからのビルド

SCons、Python 3、C++17 のツールチェーンが必要です。
Windows では MSVC、Linux では GCC か Clang です。

```sh
git submodule update --init --recursive
scons
```

ビルドの出力先は `project/addons/kimodo/bin/<platform>/` で、`project/addons/kimodo/kimodo.gdextension` が参照するのもここです。
すべてがアドオンのフォルダ内にあるので、`addons/kimodo` がリリースの中身のすべてであり、誰かがプロジェクトにコピーするものすべてでもあります。
ドックは GDScript なので、それ自体のビルドは要りません。

リリースするライブラリは単精度のみです。
倍精度の Godot を使う場合は `scons precision=double` でビルドし、対応する行を `.gdextension` に足してください。

### kmd-generate

同じ `scons` の呼び出しが kimodo.cpp から `kmd-generate` をビルドし、それが読み込む共有ライブラリとともに拡張の隣に置きます。
ドックが最初にここを見るので、ビルドが通っていれば設定なしで生成できます。

SCons が自前でコンパイルせずに CMake を駆動するのは、そのビルドを再現するには GGML と Vulkan シェーダのコンパイルまで再現することになるためです。
上記の要件に加えて、次のものが必要です。

- cmake 3.25 以降
- Vulkan SDK（GGML の Vulkan シェーダをコンパイルする `glslc` のため）
- kimodo.cpp 内の `ggml` サブモジュール（上記の `--recursive` で取得されます）

いずれかが欠けている場合は、失敗ではなく警告付きのスキップになります。
kmd-generate が以前に生成したモーションを読み、リターゲットし、保存する用途では、アドオンはそのまま動くためです。
意図的に飛ばすには `kimodo_native=no` を渡します。

Windows では、SCons が既に見つけている MSVC の環境を CMake に渡すので、開発者コマンドプロンプトは要りません。
Visual Studio のコンポーネントとして入る cmake も見つけるので、PATH に用意する必要もありません。
成果物はおよそ 55 MB で、その大半は `ggml-vulkan.dll` に埋め込まれた Vulkan シェーダです。

ターゲットごとに `kimodo.cpp/build/` の下の別のツリーでビルドするので、1 つのチェックアウトから複数プラットフォームをビルドしても CMake キャッシュを共有しません。

### kimodo.cpp へのパッチ

kimodo.cpp が文書化しているのは Linux でのビルドで、固定しているリビジョンは MSVC でコンパイルできません。
修正は `patches/` にあり、SCons が configure の前にサブモジュールの作業ツリーへ適用します。
誰にも見えないローカル変更にならず、目に見える形で残ります。
適用済みのものはスキップされます。

| パッチ | 直している内容 |
|---|---|
| `0001-narrow-path-for-gguf_init_from_file.patch` | Windows では `std::filesystem::path::value_type` が `wchar_t` なので、`path.c_str()` は `gguf_init_from_file` が取る狭い文字列になりません |
| `0002-include-stdexcept.patch` | `<stdexcept>` なしで `std::runtime_error` を使っています。libstdc++ は推移的に取り込みますが、MSVC の STL は取り込みません |

どちらも本来は上流に入るべきものです。
`.gitmodules` で kimodo.cpp に `ignore = dirty` を付けているので、パッチを当てた作業ツリーが `git status` のたびに変更として現れることはありません。
サブモジュールが指しているのは固定リビジョンのままです。

### 継続的インテグレーション

各プラットフォームを、それぞれのランナーでネイティブのツールチェーンによりビルドします。
`ubuntu-24.04` で GCC、`windows-2022` で MSVC です。
MSVC は kimodo.cpp の CMake 設定が分岐を持つコンパイラであり、上記のパッチが対象としているコンパイラであり、ggml 自身の CI が Windows 向け Vulkan ビルドに使っているコンパイラでもあります。

残りはプラットフォームごとに `.github/actions/setup-build` が導入します。
`glslc` は両者が必要とするので、Vulkan SDK も含みます。

`ci.yml` は push のたびに両ターゲットをビルドします。
`make_build.yml` はバージョン番号を与えて手動で実行するもので、両方の target type をビルドし、4 つのライブラリを収めた `addons/kimodo` を組み立て、GitHub のリリースに zip として公開します。
コミットするのは `plugin.cfg` だけです。
ビルドしたライブラリはリポジトリに入れず、リリースの成果物として配布するためです。

クロスコンパイルは可能ですが検証していません。
`KIMODO_CMAKE_TOOLCHAIN` で CMake のツールチェーンを指定し、`KIMODO_CMAKE_ARGS` で configure の行に追記すれば、ビルド側の仕組みとしてはそれで足ります。
障害になるのは、Vulkan ローダの mingw 用インポートライブラリが存在しないことです。
ggml-vulkan はこれをリンク時に要求します。

### テスト

```sh
godot --headless --path project --import
godot --headless --path project -s res://tools/verify_stage1.gd
godot --headless --path project -s res://tools/verify_stage2.gd
godot --headless --path project -s res://tools/verify_stage4.gd
```

stage 1 はファイルレイアウト、四元数の成分順、順運動学、そしてベイクした `Animation` がトラックの名指すボーンを実際に動かすことを見ます。
stage 2 はリターゲットを見ます。
`BoneMap` 越しに接頭辞付きのボーン名を持つリグ、単位行列でないレストポーズの回転、対応済みの 2 ボーンに挟まれた未対応のツイストボーンが対象です。
stage 4 は保存とライブラリ管理を見ます。

3 つとも合成のフィクスチャに対して走るので、確認できるのは配線であって、モデル自身の流儀については何も確認しません。

### プレビュー用シーン

`project/smplx_preview.tscn` はクリップを再生し、目で判断するしかないものを読み上げます。
ルート位置、両手、腰の正面ベクトル、最も低いボーンが地面からどれだけ離れているかです。
T キーでターゲットが切り替わり、素の SMPL-X レストポーズ、リターゲット経路を通した humanoid 名のレストポーズ、読み込んだモデルの順に巡ります。

実際の重みが無い場合は、まず合成のクリップを作ってください。
+Z 方向へ歩きながら左腕を上げるので、左右の反転や 180 度の向きの誤りがあればすぐ分かります。

```sh
python scripts/make_sample_motion.py project/motion_sample
```

そのうえで `project/` を Godot で開いて実行するか、実際の出力を指定します。

```sh
godot --path project -- --motion=/path/to/kmd-generate/out
```

ドラッグで orbit、ホイールで zoom、スペースで再生と一時停止、左右の矢印キーで 1 フレームずつ進みます。

### マネキン

`addons/kimodo/samples/kimodo_mannequin.glb` は 40 KB、22 ボーン、300 三角形です。
リポジトリが持っているのはモデルのソースではなく生成手順なので、編集せずに作り直してください。

```sh
blender --background --python scripts/make_mannequin.py
```

ボーンは SMPL-X のレストポーズから配置してあり、`SkeletonProfileHumanoid` の名前を最初から持っています。
プレビューがボーンマップなしで、インポート時のレストポーズ補正もなしに使えるのはそのためです。
